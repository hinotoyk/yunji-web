## 3. 模块 1 · 搜索栏（基本信息 · PROFILE 顶部）

### 3.1 背景与需求

基本信息页顶部搜索栏（`selector.js` 注入）原仅支持**四种名字**（日文名 / 欧字名 / 自译名 / 香港名）与 ID 检索，视觉普通、信息密度一般。用户诉求：默认可搜四种名字，并**额外支持母名 / 马主 / 调教师 / 生产牧场**；样式**简约、高信息密度**（契合主题：青绿 × shadcn Neutral）；只改基本信息页与搜索栏，不动其它模块。

### 3.2 选定与理由（思路）

对比「分段搜索 / 多字段筛选栏」后拍板**智能单框**：一个输入框一次匹配全部 8 类字段，最省空间、最快速，配合下拉行的字段命中标注，兼顾速度与信息密度，最贴合"高信息密度 + 简约"目标。

### 3.3 打磨迭代

1. **占位符直接提醒**：`日文名 · 英文名 · 港译名 · 自译名 · 母名 · 马主 · 调教师 · 生产牧场`，一眼看到可搜范围。
2. **下拉展示多名字**：结果行展示该马全部名字，主名加粗、其余弱化。
3. **性别用原生 牡/牝/セン**：不再翻译成 公/母/阉。
4. **名字类型区分（定稿）**：小字标签方案不可读 → 改为**彩色色块包着字体**：青绿=日文名 / 蓝=英文名 / 橙=港译名 / 紫=自译名；中间缺口显示灰块 `—`，结尾缺失省略。
5. **性别徽章配色**：`♂ 牡` `#C9EFFE` / `♀ 牝` `#FFDBD5` / `⚲ セン` `#EFEFEF`（文字加深保证可读）。
6. **整体视觉打磨**：输入框 hover/聚焦态、下拉圆角投影、选中行左侧青色竖条、下拉顶部"匹配 N 匹"计数条。
7. **计数徽章入框**：输入框右侧实时计数徽章（空态=总马数，输入=命中数青色高亮）。
8. **术语统一**：全站名字术语统一为「日文名 / 英文名 / 港译名 / 自译名」。
9. **滚动条 / 动画 / 移动端**：下拉细滚动条、150ms 淡入（尊重 `prefers-reduced-motion`）、≤768px 收紧。
10. **选中回填主名**：选完回填该马日文主名；再次点击输入框自动清空重搜；去掉 `✓ 已选` 徽章与计数，界面更干净。

### 3.4 最终落地

- **合并文件**：
  - `pages/selector.js` — 搜索组件主体（结构 + 样式注入 + 检索逻辑 + 键盘导航 + 选中回填）。
  - `pages/profile.html` — `<div id="selector"></div>` + `YJ.selector.init({el, base, onSelect})`，渲染逻辑不动。
- **实现要点**：
  1. **检索字段**（大小写不敏感子串匹配）：名字 `馬名 / 欧字馬名 / 自译馬名 / 香港馬名` + 附加 `母名 / 馬主 / 調教師 / 生産牧場` + 兼容 `id`。
  2. **下拉行**：名字彩色色块（`.nblock.jp/.en/.hk/.zh`，主名 `.main` 加粗，缺口灰块 `—`）+ 右侧性别徽章 + 出生年；命中非名字字段显示青色字段胶囊 + 命中值副行。
  3. **计数徽章** `.cnt`：空态总马数、输入命中数青色高亮；**选中回填**：回填日文主名、再次点击清空重搜。
  4. **键盘导航**：`↑`/`↓` 高亮、`Enter` 确认、`Esc` 关闭。
  5. **动效/可访问性**：150ms 淡入（尊重 reduced-motion）、细滚动条、≤768px 收紧。
- **样式**：全部由 `selector.js` 注入（`#yj-sel-css`），沿用 `theme.css` 变量（性别/名字色块为指定色值，已在本节记录）。

## 4. 模块 2 · 字体（全局排版）

### 4.1 背景与需求

用户反馈**当前字体太丑、看不清**。原 `theme.css` 是纯系统字体栈，问题：Windows 中文落到微软雅黑小字号发虚发闷、数字未全站等宽、字号过小易糊。需求：一套中/日/英混排 + 数字友好的字体方案。

### 4.2 选定与理由（思路）

关键约束：**中文/日文全量 Web 字体单字重 5~10MB**，全量引入必然拖慢。最终方案分两层：

- **拉丁/数字**：单文件可变字体 **Geist**（~29KB 覆盖全字重），本地自托管、离线可用、OFL 开源。
- **中文/日文**：默认**本地自托管思源黑体 Noto Sans SC**（101 子集按需加载）；苹方 / 微软雅黑仅作系统回退、不打包分发（授权合规）。
- 全站开启 `tabular-nums` 数字等宽，让成绩/距离/日期/赔率数字对齐。

### 4.3 打磨迭代

1. **@font-face 自托管**：Geist latin 子集 woff2（29,400B，`wOF2` magic 校验），`font-weight:100 900` 一个文件覆盖全字重，`font-display:swap`。
2. **全站字体栈**：`'Noto Sans SC','Noto Sans CJK SC','Geist','PingFang SC','Microsoft YaHei',…` —— 中文走思源、拉丁/数字走 Geist。
3. **可读性小包**：`line-height`、`-webkit-font-smoothing:antialiased`、`text-rendering:optimizeLegibility`、全站 `font-variant-numeric:tabular-nums`。
4. **字号上调**：表格 13→13.5、表头 11→11.5、字段标签 10.5→11、血统简约版 meta 7→8、行高 15→17px。
5. **界面文字放大（用户点名）**：节标题 11px 45%灰 → **14px 深色 + 字重700 + 左侧青色竖条**；表头 12.5px、字段标签 12px、KPI 标签 12.5px、徽章 12px 用深色；次要文字统一由浅灰提到深灰保证对比度。
6. **授权合规确认**：Geist / 思源黑体 = SIL OFL 开源免费商用；苹方 / 微软雅黑 = 系统内置仅回退、不打包分发。
7. **用户拍板定稿**（试衣间辅助拍板）：

## 10. 设备判定统一入口（YJ.device）+ 断点切换实时重渲染

### 10.1 背景与需求

pc / mb 判定此前散落多处且标准不一：CSS 层用 Tailwind `md:`（768px）单断点，但 JS 层 `races.html` 自写 `isMb()`（768px）、`profile.html` 用 `innerWidth>=1024`（常驻列表）。实测「桌面宽度先渲染出 PC 表格 → 切到手机」时，CSS 实时响应、但 JS 渲染的表格冻结为 PC 样式。用户诉求：**统一一个入口判定设备，pc 就走 pc 界面、mb 就走 mb 界面**，后续功能一律调用它。

### 10.2 选定与理由（思路）

- 新建共享脚本 `public/device.js`，暴露 `YJ.device.isMb()/isPc()/mode()/onChange(cb)`，**断点统一 768px**，与 Tailwind `max-md:` 同源；用 `matchMedia('(max-width:767px)')` 实现，随 CSS 实时响应、永不脱节，不支持时回退 `innerWidth`。
- **常驻列表并入 isPc**：去掉 `profile.html` 独立 1024 断点（`isWide()` 方案被否——用户明确「不要幺蛾子」），常驻列表/双栏由 `isPc()`（≥768）统一决定；配套 CSS `max-lg:`（1024）全部拉齐 `max-md:`（768），消除「判 pc 却单列」中间态，符合 AGENTS.md「统一 max-md 单断点」。
- **断点翻转实时重渲染**：`races.html` 订阅 `YJ.device.onChange()`，pc/mb 翻转时用缓存 `lastR` 免请求重渲染当前马。

### 10.3 打磨迭代

1. 盘点散落判定：`races.isMb`（768）/ `profile` innerWidth（1024 两处）→ 收敛到 `YJ.device`。
2. 首版保留 `isWide()`（≥1024）当「布局决策」→ 用户拍板统一 → **删除 isWide/WIDE**，常驻列表并入 `isPc()`。
3. 断点拉齐：profile 双栏 6 处 + selector 常驻 2 处 `max-lg:` → `max-md:`，构建后复检 theme css 含新类、无 max-lg 残留。
4. 复现「桌面渲染后切手机仍 PC 表格」→ 加 `onChange` 免请求重渲染修复，PC/mb 双端切换实测通过。

### 10.4 最终落地

- **合并文件**：
  - `public/device.js`（新增）— 统一入口：`isMb()/isPc()/mode()/onChange()`，768px，matchMedia。
  - `pages/races.html` — `isMb()` 委托 `YJ.device.isMb()`；`lastR` 缓存 + `YJ.device.onChange` 断点翻转重渲染。
  - `pages/profile.html` — `persistent: YJ.device.isPc()`；滚动分支改 `isMb()`；双栏/常驻 CSS `max-lg:`→`max-md:`。
  - `public/selector.js` — 常驻列表断点 `max-lg:`→`max-md:`。
- **后续用法约定**：页面加 `<script src="../device.js"></script>`，分支写 `if (YJ.device.isPc()) {…} else {…}`；依赖渲染形态的功能在设备翻转时用 `YJ.device.onChange` 重渲染。

## 23. 比赛记录·宽屏列宽 v6（全列参与分配 + 密度分档）

### 23.1 背景与需求

  ② **分配只决定留白摆在哪，不改变留白总量**（总量 = 1 − 内容宽 ÷ 容器宽，由屏宽 ÷ 字号决定）。

### 23.2 选定与理由（思路）

- 四条候选（临时对比页 `tests/_scratch/colwidth/` 同屏并排实测）：
  A 只分配 / B 分配+升档到留白 ≤45% / **C 分配+升档到留白 ≤40%** / D 整页封顶 1560px 居中。

### 23.3 打磨迭代

1. 升档判据从「分配后余量」改为「**表内留白占比**」——余量会被软上限吃掉，屏再宽也不一定触发升档；用户感知的「空不空」就是内容宽 ÷ 容器宽。

## 24. 比赛记录·等级徽章 L / OP 不可见修复（类名大小写）

### 24.1 现象

级别筛「L」「OP」时，赛事名后面本该有的金色 `L` 徽章、浅青绿 `OP` 徽章都看不到；G1/G2/G3 徽章正常。

### 24.2 原因

- `<style>`：底色由 `.yj-gl` / `.yj-gop` 提供，`.yj-grade` 只写 `color:#fff`（白字）。
- JS：等级→配色表 `G` 里写的是 `"L":"gL"`、`"OP":"gOP"`，渲染出来是 `class="yj-grade yj-gL"`。
- **HTML 的 class 选择器区分大小写** → `.yj-gl` 匹配不上 `yj-gL` → 没有底色 → **白字落在白卡片上 = 看不见**。
- 这是老 bug（v5 时代就在），只是模块 22 去掉赛事名里的 `(L)`/`(OP)` 文字尾缀后，等级信息只剩徽章一条路，才暴露出来。

### 24.3 修复

- `G` 取值统一改小写：`"L":"gl"`、`"OP":"gop"`，与 `.yj-gl` / `.yj-gop` 一一对应。
- 两处都补注释：**G 的取值必须与 `<style>` 里的 `.yj-g*` 类名完全同大小写（全小写）**，否则徽章无底色、白字不可见。

### 24.4 验证

| OP | `yj-grade yj-gop` | `rgba(10,167,160,.15)` 浅青绿 | `rgb(10,122,117)` | ✅ |

### 24.5 新增/修改等级徽章时的注意事项

三处名字必须完全一致（全小写）：

1. `G`（等级 → 类名后缀，如 `"GI":"g1"`）；
2. `<style>` 里的 `.yj-g1{background-color:…}`（写死色值属允许的「指定色块」）；

- 根因（v6 遗留）：注水上限是全局常量 `CAP_TXT 2.0 / CAP_NUM 1.5`。赛事名列（idx 3）是 21 列里 base 最大、且带级徽章额外宽的文本列，v6 的 `fill()` 按 base 占比分配 slack → 赛事名分到最多 slack，27 寸直接顶到 2.0×（约 600px），14 个数字列恒卡最小宽（§23.1 实测 1.0–1.2×）。

### 26.2 选定与理由（思路）

- **方案：上限从「全局常量」改为「随档位表」**——`TIER_CAP = {档位: {race, txt, num}}`：
  - `race` 赛事名列单独上限（唯一内容超长 + 带徽章的文本列，最容易独大）；
  - `txt` 其余 6 个弹性文本列；`num` 14 个数字列；
  - 档位越高（屏越大）→ race/txt 收窄、num 放宽。
- 落选：给赛事名固定 px 上限 / 按容器宽 if-else 特判 —— 前者在档位 0 下 slack 小、上限永远撞不到（无效改动），后者违背「一套方案」诉求。
- **关键推导**：15/24 寸（≤1700px 容器，档位 0）slack 被弹性列吃光、**撞不到上限** → `TIER_CAP` 档位 0 写 v6 原值（2.0/2.0/1.5）→ 行为与 v6 完全一致；只有 slack 足够大（27 寸档位 4）上限才生效。

### 26.3 打磨迭代

1. `fill()` 签名从 `(…, cap)` 改为 `(…, capFn)`：capFn(i) 返回该列软上限倍数（null=不限量），单次注水即可支持「赛事名单独上限」。
2. 第三阶段「余量全表均分」也走 capFn：赛事名封顶在 race，不再被均分二次撑宽（超宽屏兜底）。
3. 档位 0 保留 v6 原值 → 15/24 寸逐列 0 变化；中间档位 1–3 按比例过渡（25 寸 ~1900px 容器会命中档位 1）。

### 26.4 最终落地

  1. 删全局 `CAP_TXT / CAP_NUM`，新增 `TIER_CAP`（5 档 × race/txt/num）；

1. **级别初胜**：OP / L / G3 / G2 / G1 / Jpn1 / Jpn2 / Jpn3 **每个级别的产驹史首胜，全局只出现一次**（2026-09 确认为全局口径，不再按马——初版按马生涯首次，导致不同马的同级别首胜重复挂标；未胜利/班赛不单列；按马计的「新马初胜」过噪，改为按世代只记第一条，见下条）；
2. **世代首个新马胜**：每个世代最早的新马战一着，一代只此一条（如 ルージュボヤージュ = 2023年产首个新马胜）；
3. **重赏胜利**：所有重赏一着都记录。~~序数按马独立计数~~ → **全局序数**（2026-09 用户确认为产驹史口径，跨马按日期累计）：每场重赏一着挂「首个重赏（N=1）/重赏第N胜」+ 该级别「G2第N胜」，海外重赏另挂全局「海外重赏第N胜」；马内不再记同级别序数（G2初胜 等级别初胜仍按马）；
4. **世代首个重赏**：每个世代（=生年/生产年）产驹在 **JRA 中央**的首场重赏胜利，一代只有一条（如 ゴーイントゥスカイ = 2023年产首个重赏；同世代之后赢再多也不重复标记）；
5. **父子制覇**：产驹赢下コントレイル（飞机云）赢过的重赏——常量抓自 `db.netkeiba.com/horse/result/2017101835/`；
6. **受赏**：读 `basic.json` 新预留的 `受賞歴` 字段（每匹马 `[]`，后续由后端/手动填充）。

**展示口径**：纯展示、无筛选；**时间自下而上——最新事件在顶部**，年份分组降序（2026→2025）。

**重复值方案（用户问点）**：一场比赛 = 一条事件，**绝不按标签拆行**；该场触发的所有里程碑以多枚标签徽章并列挂在同一张卡上（如 青葉賞一着 = `[G2初胜] [2023年产首个重赏]` 两条并存）。级别第 1 胜只显示「初胜」，从第 2 胜起显示「G1第 N 胜」，不重复挂。

### 31.2 选定与理由（思路）

- **事件引擎前置（后架构：已下沉后端）**：先算「每世代首个中央重赏 + 每世代首个新马胜」两张映射，再逐马按日期正序扫（`seen` 级别初胜 / `cnt` 级别序数 / `ovs` 海外重赏序数），全部只依赖现有字段（`格`/`結果`/`venue_type`/`レース名`/`生年`），数据更新零维护。
- **架构升级（后端预计算）**：`scripts/timeline/build_timeline.py` 读 basic.json + races/*.json → 生成 `data/timeline.json`（渲染就绪事件：日期/类型/节点/马/图源/标签含 tooltip + meta.stats，**字段模板全文写在脚本头部 docstring**），`run_update.py` 各数据策略（basic/races/horse/races-force/ledger/ci）末尾自动重算，--ci 在 git 提交前跑、产物随 data/ 入库；**全量重算 + 内容签名比对，无变化跳过写入**（避免 generated_at 造成空 diff 提交）；前端改为 **fetch 1 个 JSON → 纯渲染**（277 请求 → 1 请求，页面 15.8→10.1 kB）。迁移用 `tests/_trash/timeline_compare.js` 做旧 JS 引擎 ↔ Python 产物逐事件 diff，6/6 完全一致后才切换；父子制覇常量随之并入 Python，`front/public/sire-wins.js` 删除。
- **人工节点（用户手记，重算不覆盖）**：编辑 `data/timeline_manual.json` 的 `events` 数组即可添加特别时间节点（模板见该文件 `_readme`：date/title 必填，cn/note/link/photo/tags 可选）；`build_timeline.py` 每次把它**合并**进产物并按日期排序（`"manual": true` 标记自动打上，节点取中性灰 `manual` 色系，缺失 horse 不计入覆盖产驹数），**该文件本身永不改写**；缺 date/title 跳过并告警；读取用 utf-8-sig（兼容 Windows 记事本 BOM）。前端 eventHTML 有 manual 分支（📌 标题+副题+说明+可选跳转链接），smoke 用合成样例常测该分支。
- **父子制覇判定**：`レース名` 去尾部格级括号（`東京優駿(GI)`→`東京優駿`）后与常量 `name` 精确匹配；常量含自译中文名，悬停 tooltip 显示「飞机云同胜：皋月赏」。
- **独立页而非 profile 内嵌**：时间线是全站叙事（跨马混排 + 世代事件），不挂单马；马名经 `hjump` 跳 `profile.html?horse=id` 与 races 页一致。
- **中央轴布局**：轴线居中贯穿（`.tl::before` 50%），卡片为 16:9 标准矩形（`aspect-ratio:16/9`、宽 `min(480px,100%)`，内容垂直居中不强行铺满），按序左右交替；日期在卡片对侧、与节点垂直居中；年份为骑在轴线上的居中胶囊；mb（≤768px）退回单列左轨、卡片取消定比改自适应高。
- **事件卡 v3（图+文两栏）**：卡高**随内容自适应**（16:9/3:2 定比时 A4 横图上下留白 75px 过空，弃用定比；卡片高度=max(图盒+白边, 文字列)）；图列 `.tl-photo` 宽 50%、`margin:10px`+圆角 4px（横放 A4 比例 `aspect-ratio:297/210`≈√2:1、`align-self:center` 垂直居中浮于轴侧，不顶死卡缘；object-cover 裁切、贴时间轴一侧——`.right` 卡图在左缘、`.left` 卡 `order:2` 翻到右缘；mb 44%）+ `.tl-body` 文字列（赛名 15px 粗 / 场地 meta 灰行 / ❶马名 16px 粗+译名 / `.tl-kpis` 三格 / 騎手·調教師灰行 / 标签行）。图源 `r.photo` 优先、回退 `h.photo`，数组/字符串兼容（同 profile 头像约定）；无图=`.tl-photo.empty` 浅灰底+🐎占位，保持卡片节奏统一。`photo` 字段已预留进全部 721 条比赛记录（merge 只追加不重写已有条目，字段安全）。
- **卡片 DOM 结构防坑**：卡片 DOM 一律 `tl-cardwrap > tl-card > [tl-photo, tl-body]`，拼串时壳层开闭必须成对；smoke 护栏断言整页 div 配平。
- **纯展示**：无筛选（初版做过类别+世代 chip 筛选，用户砍掉）；时间自下而上——渲染前倒序，最新事件在顶部，年份分组降序，节点/竖线连续性不变。
- **事件卡四行结构（文字排版稿用真实数据与用户逐行确认）**：①标题行 = 等级徽章 + 赛事名（14px 半粗），右侧 `場名+R · 芝/ダ距离 · 馬場` 灰字右对齐；②主角行 = ❶金色1着块 + 马名（15px，可点跳 profile）+〈港译/自译〉+ 右侧 `騎手 · 斤量 ｜ 調教師`；③数据条 = タイム（青绿加粗）/ 上り / 人気 三格，label 上、值下、细竖线分隔，mb 自动换行；④标签行 = 里程碑徽章。着差字段因 1着 值为 `-0.1/0.0` 型秒差、语义不可用未展示；単勝/頭数/馬体重/天候按用户取舍不放。
- **样式**：复用 races.html 的等级徽章/1着徽章体系；事件标签 5 色按类别区分（初胜=青绿、重赏=深蓝、世代=橙、父子制覇=红、受赏=金），轨道节点取该事件最高优先级标签色；`max-md:` 单断点下日期并入卡片上方。

## 32. 日期图页（日历布局稿 v2）

### 32.1 背景与需求

- `pages/datechart.html` 原为纯占位页，且占位文案有误（「切换：柱状图…」多冒号）。用户给出修正文案后先做过一版**柱状图稿**（天/周/月/年柱 + 单位明细），用户过目后提出新预期（v2 定向）：
  1. **改成日历图形式**；
  2. 天/周/月/年 每个口径要**快速读出**：进板数 `[第1-第2-第3-第4-第5-5名之外]`（=着顺分布 6 段）与**总赏金**；
  3. **重赏要有额外标识，最好是「图标+数字」组合**（🏆 n）。

### 32.2 选定与理由（思路）

- **日历为骨架、口径为聚合范围**：日历网格不变，天/周/月/年 只切换「KPI 汇总范围 + 高亮」——月=整月网格；周=所在 ISO 週行描边高亮；天=选中格描边（点任意格切换）；年=12 张月卡。点格下钻（月/周 → 天，年 → 月），‹ › 按口径步进（天±1日/周±7日/月±1月/年±1年），边界从数据推导、自动禁用。
- **KPI 带（口径汇总，回应「快速知道」）**：出走 / 胜 / **进板数**（`[a-b-c-d-e-f]` 六段，数字按数据语义色：1着=primary 青、2着=chart-2 蓝、3着=chart-3 橙、4-5着=深灰、5名之外+未完走=浅灰；悬停提示各段含义）/ **总赏金**（万円，无出走=—）/ **重赏胜**（🏆 n，>0 青绿高亮）。
- **日历格逐日信息**：日期 + 进板数缩写 + 当日赏金，右上 `🏆n`（当日重赏胜数）；有出走无胜=浅灰底，有胜=按胜数分档的青绿底（1/2/3+ 三档），有胜日日期数字染主题青；mb（≤768px）格内只留 日期+🏆（进板数/赏金收进 KPI 带与明细）。
- **明细列表**：口径内**全部出走**（不再是只列胜场），PC 7 列表（日期/马名/赛事/场地/距离·跑道/**着顺**/**赏金(万円)**，着顺 1/2/3 用 races 同款色块徽章、未完走整行降灰）；重赏**胜**行 = 🏆 + 等级徽章 + 整行浅青底；mb 软分行卡片同构。
- **数据留空、交互做实**：示例数据 = 库内真实出走记录 188 场（2026-08~09 全量 + 2025-07~2026-06 各代表日，含 1-5着/着外/未完走/GII/GIII/L 各形态，由脚本从 `data/races` 生成注入），格式与真实记录一致；**接入真实聚合时只需把 `RUNS` 换成数据源，渲染层不变**。

### 32.3 最终落地

- **合并文件**：`pages/datechart.html` 单文件。

  2. `<style>`：`.yj-grade`/`.yj-no`（同 races）、`.seg`/`.dc-nav`、`.dc-kpis` KPI 带、`.dc-brk` 进板数配色、`.dc-cal`/`.dc-wrow`/`.dc-cell` 日历、`.dc-ym` 月卡、明细行 `.dc-grow`/`.dc-dnf`、mb 卡片与 ≤768px 收缩（其余全 Tailwind utility）。

## 33. 比赛记录·同日按发走时间细分排序（内嵌/独立 × PC/MB 四处统一）

### 33.1 背景与需求

- 比赛记录此前只按**日期**排序（独立跨马表日期降序；内嵌单马表用 JSON 原始顺序，也是日期降序），同一天内的多场比赛顺序不稳定——独立模式是全库跨马查询，同日几十条记录顺序取决于加载序。用户要求（经一次口径修正定稿）：**同一天比赛按発走（发走时间）从大到小排；没有发走时间的默认是最大**——即降序下缺失発走排在同日最前（现存 9 条缺失均为海外赛）；内嵌（profile 下段）与独立页、PC 与 MB 全部生效。

### 33.2 实现思路

- **数据事实**：`発走` 为零填充 `"HH:MM"` 字符串（全库 740 条均 5 位，可直接字符串比较），仅 9 条缺失（空串，均为海外场）；`日付` 为 `YYYY-MM-DD`。故排序无需解析时间，字符串比较即可。
- **统一比较器 `raceCmp(a, b)`**（`pages/races.html` 工具区）：①日期降序（新→旧，保持现有方向）；②同日 `発走` 降序（大→小）；③缺失/空串视为最大，降序下排同日最前；④完全同键（跨马表同一场比赛的多匹马）返回 0，走 `Array.prototype.sort` 稳定性保持加载顺序，不引入任意次级键。
- **两处接入，四处生效**（PC 表与 mb 卡片渲染同一份有序列表）：

  - **独立模式**：`renderResults` 里原 `日付 localeCompare` 一行替换为 `raceCmp(a.r, b.r)`——筛选/翻页/设备切换每次重排，行为不变只加次级键。
- **零改动**：渲染函数（rowHTML/rowMbHTML/rowEmbedHTML/rowEmbedMbHTML/libRowHTML/libRowMbHTML）、i18n、数据、其它页面。日期图页明细表（datechart.json 无発走字段）不在本次范围。

## 43. 通算战绩/成绩改「连体底色 + 保留 - 连字符」（修正 §41 理解偏差）
