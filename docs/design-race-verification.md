# 设计方案：netkeiba 比赛记录校验 + 差异审核 + 防覆盖（需求 2/3/4）

> 状态：**待用户过目确认**，确认后按阶段实施。
> 关联：`docs/data-contracts.md`（契约分层）、`云迹项目.md`（规格书 v2）

---

## 0. 一个必须修正的事实（影响设计）

**netkeiba 的比赛记录不在马匹基本信息页上**。实测（多匹马，含コントレイル本人）：

- `db.netkeiba.com/horse/{id}/`（基本信息页）→ **只有资料表，无任何成绩表**
- `db.netkeiba.com/horse/result/{id}/`（**独立成绩页**）→ 生涯全成绩表 `db_h_race_results`，33 列，含需求全部字段（日付/開催/天気/R/レース名/頭数/枠番/馬番/オッズ/人気/着順/騎手/斤量/距離/馬場/タイム/着差/通過/ペース/上り/馬体重/賞金）

**结论**：无法"抓基本信息时顺带抓比赛记录"，每匹马需 **+1 次请求**（result 页）。增量策略见下，实际增量压力很小。

## 1. 契约D：netkeiba 比赛记录（需求 2）

### 1.1 定位
- **只落库、不展示**；唯一作用 = 校验台账（契约B）数据是否有误
- 现阶段展示仍以台账为准；未来可能切换为 netkeiba 为准 → **必须解耦**（存储/比对/合并三处独立）

### 1.2 存储
```
data/raw/netkeiba_races.json     # 契约D：按马组织 { nk_id: [ 场记录... ] }
```
每场记录（规范化字段，与台账字段对齐以便比对）：
```json
{
  "日付": "2026-08-15", "開催": "2中京7", "場名": "中京", "天気": "曇", "R": 4,
  "レース名": "3歳未勝利", "頭数": 14, "枠番": 6, "馬番": 9, "オッズ": 131.6,
  "人気": 12, "着順": 13, "騎手": "中井裕二", "斤量": 55.0, "距離": 1400,
  "馬場": "芝", "状態": "良", "タイム": "1:20.9", "着差": "1.1", "通過": "12-12",
  "ペース": "33.8-34.2", "上り": "34.2", "馬体重": 420, "増減": "+4", "賞金": 0
}
```
字段转换规则（result 页原生值 → 契约D）：
| 源 | 转换 |
|---|---|
| 開催 "2中京7" | 拆出 場名=中京（回次/日目 保留） |
| 距離 "芝1400" | 拆出 距離=1400 + 馬場=芝（ダ→ダート） |
| 馬場 "良" | → 状態（与台账口径一致） |
| 馬体重 "420(+4)" | 拆 420 / +4 |
| 日付 "2026/08/15" | → 2026-08-15 |

### 1.3 抓取方式（`scrape_netkeiba.py --races`）
- 遍历 crops.json 中**已出赛马**（当前 135 匹），请求 `db.netkeiba.com/horse/result/{id}/`
- **增量跳过**：netkeiba_races.json 已有该马记录 且 其最新日付 ≥ 台账该马最新日付 → 跳过（无新比赛，不重抓）
- 首轮全量 ≈ 135 请求 × 6.5s ≈ **15 分钟**；之后每周定时只重抓"有新比赛的少数马"（几分钟）
- 请求间隔沿用 netkeiba 5-8s 档；写入 fetch_log.csv 一并观测

### 1.4 解耦保证
- 契约D 独立文件，不比对不合并进 crops
- 未来"以 netkeiba 为准"：只需把 build-data 的合并源从契约B 换成契约D（+ 字段映射），架构已预留

## 2. 差异比对（需求 3 前半）

`scripts/compare-races.py`（新）：
- 匹配键：`馬名 + 日付 + R`（netkeiba 有 場名 可再加一层校验）
- **字段级比对**（仅共有字段：日付/場名/天気/R/レース名/頭数/人気/オッズ/着順/騎手/斤量/距離/馬場/状態/タイム/着差/上り/馬体重/賞金）
- 台账**缺失列**（馬番/通過/ペース）→ 不比对，netkeiba 值作为"可补强提示"
- 输出 `data/race-diffs.json`：
```json
[{ "馬名": "…", "race_key": "2026-08-15|中京|4", "field": "着順",
   "ledger": "5", "netkeiba": "4", "action": "pending" }]
```
- 汇总报告写入 `data/race-diffs-report.md`（按马/按字段统计差异量）

## 3. 差异审核页（需求 3）

新页面 `page/review.html`（差异审核中心）：

- 加载 `data/race-diffs.json`，按马分组展示
- 每条差异三选一：**采用台账 / 采用netkeiba / 自定义**；另提供 **标记忽略**（确认无误，不再提示）
- 确认结果写入 `data/race_overrides.json`（= 用户裁决记录，见第 4 节）
- 顶部：差异统计卡（总数/待审/已确认/已忽略）+ 批量操作（同马同字段一键采用某侧）
- 构建流程：`compare-races.py` 产 diff → 用户审核 → 裁决进 overrides → build-data 落盘 → 展示

## 4. 全局防覆盖层（需求 4，核心）

### 4.1 问题
现状：人工字段（译名/近况/血统分析/备考）存在 crops.json 里，全量抓取 + build-data 重建时会**被覆盖**；未来比赛裁决值也有同样风险。

### 4.2 方案：`data/overrides.json` 用户权威层

```
netkeiba 基本信息 ──契约A──┐
台账 ───────────────────契约B─┼─→ build-data.py ──► crops.json ──► 前端
netkeiba 比赛记录(result页) ──契约D─┘        ↑
                                          │ 应用 overrides（最高优先级，永不覆盖）
                          data/overrides.json ◄── review.html（裁决）/ admin.html（人工修改）
```

结构：
```json
{
  "アオイハルカ": {
    "译名":   { "v": "蓝燕", "ts": "2026-08-18 10:00", "note": "人工补录" },
    "調教師": { "v": "杉山晴紀", "ts": "…", "note": "修正抓取截断" }
  },
  "アオイハルカ#2026-08-15|中京|4": {
    "着順": { "v": 4, "ts": "…", "note": "差异审核：采用netkeiba" }
  }
}
```

规则：
- **键**：马名（马档案字段）或 `马名#日付|場名|R`（单场比赛字段）
- **优先级**：overrides > 源数据。build-data 合并时：先取契约A/B/D 源值，再应用 overrides → crops.json。**用户确认/修改过的字段永远不被后续抓取覆盖**，除非用户主动删除该条
- 译名/近况/血统分析/备考 等人工字段**迁入 overrides 层**（admin.html 改为写 overrides.json）
- review.html 的裁决、admin.html 的修改，统一走 overrides.json（单一入口）
- overrides.json 进 git 版本管理，可回溯；不随全量抓取变化

### 4.3 迁移
首次启用时：把现有 crops.json 中人工字段（译名/近况/血统分析/备考）**一次性搬进 overrides.json**，此后它们受保护。

## 6. 风险与限制

1. result 页每马 +1 请求（增量后仅新比赛马，压力小；已计入风控观测）
2. 文本值差异需要格式化对齐（タイム、馬体重、オッズ 等），比对脚本做归一化；无法归一化的进"待人工"清单
3. 台账停维护后：合并源 契约B → 契约D 一处切换，overrides 层不变（架构已支持）
4. 审核页确认的裁决若与后续新抓取再冲突：新差异会重新出现，需用户再次裁决（可在 overrides 里标记"此字段以后一律以某侧为准"来一劳永逸）
