## 0. 变更摘要（v1 → v2）

| 环节 | v1（现状） | v2（本方案） |
|---|---|---|
| 新马发现 | 手动 `--all` 全量扫列表 | **每日列表对账**（廉价增量）+ 新马自动建档 + 改名处理 |
| 马匹身份 | 无（按规范化马名合并） | **本地自增 id + registry 映射表** |
| 基础信息 | netkeiba 主 / JBIS 兜底 | 不变；+ JRA 一次性补 `馬名意味` |
| 血统 | netkeiba 全量 / JBIS 兜底 | **一次性 + 遗漏重试**（`血統_ok` 标记） |
| 比赛记录 | Google Sheets 台账（权威源） | **netkeiba 成绩页聚合（主）** + 台账海外补缺/兜底（双轨制：台账检测 7/30 天 + 轮换 50匹/天） |
| 収得賞金（平地/障害） | 无 | **计算**（racelib 规则表，非抓取） |
| crops.json | 裸数组（407 匹） | `{_meta, horses[]}` + **facet 检索索引** |
| 定时任务 | 只拉台账 | 每日：对账+成绩+构建；每周：血统重试 |

**核心原则不变**：数据流通与数据源无关；每层只消费契约；crops.json 仍是前端唯一数据源。

## 1. 数据源决策（已拍板）

| 数据 | 主源 | 辅助/兜底 | 仲裁 |
|---|---|---|---|
| 新马发现 | **netkeiba 産駒一覧**（唯一按种马浏览的公开入口） | JBIS 産駒一覧（登记滞后，交叉核对） | — |
| 基础信息 | **netkeiba** | JBIS（netkeiba 无记录的马） | JRA（争议时人工核对） |
| 馬名意味 | **admin 人工补录**（默认；JRA 马页人工查看） | Playwright 一次性回填（可选，未来）——**纯 requests 抓取不可行**（JS token 机制，2026-08-18 实测） | — |
| 血统（5代/FNo/クロス） | **netkeiba** | JBIS（一次性 + 遗漏重试） | — |
| 比赛记录 | **netkeiba 成绩页** `/horse/result/{id}/` | Google Sheets 台账（海外补缺/兜底，双轨制覆盖，见 §5） | — |
| 収得賞金 | **计算**（规则表，见 §4） | JRA 页面值仅作抽查校验 | — |

选型理由（要点）：
- JRA DB 无种马産駒浏览、无批量列表、ID（DBNUM）与 netkeiba 无公开映射、抹消马分库、海外/地方不覆盖 → 只配当"仲裁员"。
- netkeiba 成绩页天然聚合 中央+地方+海外，一个 nk_id、一个格式 → 比赛主源。
- JBIS 血统表生来即定、终身不变 → 抓一次 + 空洞重试即可，全量重抓纯亏（还吃 403 限流）。

## 2. 新马发现与改名链路（每日增量）

### 2.1 身份锚点 = nk_id（不可变），名字 = 可变字段

netkeiba 给未命名仔建档时就用同一 nk_id（如 `イリデの2025` → `2025107965`），正式命名后**页面与 ID 不变，只改名字**。因此"改名"不是新马，是同一条记录更新名字：

```
每日列表对账（--new 模式）：
  抓列表页（~5 页）→ 按 nk_id 与现有数据 diff：
  ├─ 新 nk_id      → 建档 stub（占位名也建），当天补详情页基本信息，血统留待周重试
  ├─ nk_id 相同、名字不同 → 原地改名：names 追加新名，旧名进"曾用名"，不产生新条目
  └─ nk_id 消失    → 不处理（已拍板）
```

### 2.2 占位名规则

| 源 | 占位名形态 | 识别 |
|---|---|---|
| netkeiba | `ナイトオブイングランドの2025` | 正则 `の(19|20)\d{2}$` |
| JBIS | `母名＿2025` | 含 `＿` |

- 占位名不能作为身份匹配依据（不同母马有大量同名形态"〇〇の2025"），**必须走 nk_id**。
- `test-data.py` 断言：有 races 的马不允许带未命名标记（出过赛必有正式名）；nk_id 全库唯一。

### 2.3 每日流水线（GitHub Actions）

```
每日 UTC22:00（JST07:00）:
  scrape_netkeiba --new     列表对账（~5页）+ 新马建档 + 改名处理   ← 廉价，分钟级
  pull_races                台账（Google Sheets）拉取 → ledger.csv   ← 海外数据先落盘（容错：失败沿用上次）
  scrape_netkeiba --races   成绩页双轨制增量（Track A 台账检测 7/30 天窗口 + Track B 轮换 50匹/天）
  build-data                合并（netkeiba 主 + 台账海外补缺/兜底）+ 収得/facet 计算
  test-data                 断言（唯一性/占位名/海外来源策略/収得快照）
  commit & deploy
每周:
  scrape_netkeiba --ped     血统空洞重试（新马 + 空洞）
  scrape_jbis --fill        JBIS 兜底：登记滞后马
```

## 3. 身份层：本地自增 id + registry 映射表

外部 id（nk_id/jbis_id）是**属性**不是**身份**。身份 = 本地自增 id（未来海外出道马无任何外部 id，本地 id 保证一定有）。

### 3.1 registry.json（映射表）

```json
{
  "horses": [
    {
      "id": 1,
      "keys": { "nk_id": "2024100596", "jbis_id": "0001345678" },
      "names": ["ナイトオブイングランドの2025", "レッドスカイ"],
      "生年": "2025",
      "created": "2026-08-10", "updated": "2026-09-12"
    }
  ]
}
```

- `names` 按时间顺序追加：**末位 = 当前名，其余 = 曾用名**（保留，前端可展示"曾用名：…"；与 exec M1.3「当前名 = names[-1]」、§6.1 crops 示例一致）。
- **id 分配：不设计数器字段（无 `next_id`）**——每次构建扫描现有 id 取 `max+1` 自增。build-data 是唯一写入方、无并发，安全且少维护一个状态。
- **id 语义 = 出生日期顺序**：种子按 `生年月日` 从小到大排序分配（缺失退 `生年`，再缺排末位；并列按马名稳定排序），**最年长 = id 1**。此后新马一律 `max+1`（新发现必为更新幼驹，天然落在尾部）。
- registry 同时充当"外部键 → 本地 id"的映射表。

### 3.2 身份解析顺序（build-data 每次构建）

```
1. 源记录带 nk_id   → registry 查 nk_id → 命中沿用 id
2. 源记录带 jbis_id → 同上
3. 都没有           → 用 (馬名, 生年) 查 → 命中沿用；未命中 → 分配新 id（max+1）
```

### 3.3 边界情况

| 场景 | 处理 |
|---|---|
| 改名（占位名→正式名） | nk_id 命中同一 id，names 追加新名；**旧名不删除**（曾用名） |
| JBIS 兜底马被 netkeiba 收录 | jbis_id 已建档 → 后续 nk_id 补进 keys，不重建 |
| 海外出道马（无外部 id） | 走第 3 条，(馬名, 生年) 建档 |
| 台账独有马自动建档 | 同样分配 id 进 registry |
| nk_id 消失 | 不管（已拍板） |

### 4.2 时间规则（"会不会过期"）

- **収得賞金是生涯累计值：不过期、不衰减**，不是积分制（置信度 高）。
- **2歳赛季収得 → 3歳后折半：未确认，疑似已被 2016 年（平成28年）番組改正废止**。88 次检索未找到该规则的现行条文；背景记忆中"曾存在"，2016 改革可能删除。→ **实现默认不做折半**，规则表留配置开关（`HALVE_2YO: false`），待 JRA 页面抽查确认后定。
- 抹消/引退 → 冻结为最终值（高）；中央抹消→地方移籍 → 中央収得停止加算（高）；地方→中央復帰换算：JRA 侧条文未取到，**不做**，标注口径"仅中央収得"。
- 海外重赏：存在"外国の重賞競走"算入框架（平成7年理事長達第63号 別表），但**未取到现行细则**，暂不计入，标注口径。

## 5. 比赛记录：契约B = 统一格式，双适配器

契约 B 是**数据契约（字段/值域定义），不是数据源**。改主源后它变成两个适配器的共同输出：

```
netkeiba 成绩页 ── adapters/netkeiba_races.py ──▶ 契约B 记录（主）
Google Sheets   ── adapters/sheets_ledger.py ──▶ 契约B 记录（补漏：海外）
                          │
                          ▼  build-data：按 (日付, 場名, R) 去重，netkeiba 优先，台账补缺
                    统一比赛记录 → races[]
```

- 每条记录加 `來源: "netkeiba" | "ledger"` 溯源。
- **比赛记录一旦发生不再变化** → 成绩页/比赛页全部按"抓一次终身有效"处理，**只做增量**：每日只抓新场次（含新马的整条履历），旧场次永不重抓。
- **台账每日拉取**（Google Sheets → ledger.csv），**仅保留海外场次参与合并**（venue_type=海外 = 非 JRA/NAR 场地）：中央/地方的台账记录由 netkeiba 覆盖，合并时丢弃。
- **海外场次合并策略（2026-08-19 用户拍板）**：netkeiba 视为"**可能没保存这场**"——netkeiba 有该场 → **netkeiba 优先**（來源=netkeiba），台账只补空缺字段（当前 `OVERSEAS_FILL_FIELDS=["賞金"]`，可扩展）；netkeiba 无该场 → **台账展示**（來源=ledger）。netkeiba 海外场 R 常为空 → 同 (日付, 場名) 松散匹配。
- **增量双轨制（2026-08-19 用户拍板，消除"已建档马新场次不被发现"盲区）**：
  - **Track A 台账辅助检测（快）**：`ledger.csv` 全量行（中央/地方/海外）作"应该有哪些场次"驱动——台账有 netkeiba 尚缺的场次、且比赛日在窗口内 → 抓该马；窗口 **中央/地方 7 天、海外 30 天**（台账快于 netkeiba 的追赶期，状态可重入：窗口内天天重抓直到 netkeiba 补上；超窗口 → 停快通道，由 Track B 兜底）。
  - **Track B 轮换兜底（慢但全）**：循环队列 `data/raw/rotation_queue.json`（含全部有 nk_id 的马，现约 406 匹），每天取 head 起 **50 匹**抓全量成绩页，head 前进 50（模长，**约 8 天一轮**）；新马自动追加尾部；兜住台账没记的新场次与 netkeiba 侧修正。
  - 两趟**去重**（同一马一天只抓一次）；之后统一 `backfill_honsho`（本賞金）。显示策略不变：台账中央/地方仍丢弃、海外仍 netkeiba 优先 + 台账兜底（口径：賞金合計 = 中央 + 地方）。
- 换源（如未来接 NAR 官方）只需再写一个适配器，下游零改动。

### 5.1 骑手全名：jockey_id 字典（netkeiba 全站截断，已实测）

**已证实（2026-08-18 数据实测 + 用户页面验证）**：netkeiba 对 5 字骑手名**全站截断为 4 字**——马匹成绩页、比赛结果页均显示 佐々木大（全名佐々木大輔）、柴田裕一（裕一郎）、永島まな（まなみ）…共 9 例；≤4 字名（武豊、北村友一）完好。`賞金(万円)` 列正常显示。调教师/马主当前数据无截断。

**方案（全名仍来自 netkeiba，按 jockey_id 解析）**：

1. **解析时提取 jockey_id**：成绩页/比赛页的骑手单元格是 `<a href="/jockey/result/{id}/">佐々木大</a>`——**文字截断、链接 id 完整**。`parse_races` 增加 jockey_id 提取，写入每条契约B 记录。
2. **骑手字典一次性建立** `data/jockeys.json`：`{jockey_id: 全名}`。对每个 distinct jockey_id 抓一次骑手页 `/jockey/result/{id}/`（页头显示全名，**2026-08-18 用户已验证 ✓**：佐々木大→佐々木大輔）；骑手集合有界（当前 ~104 个），一次抓完终身有效。
3. **构建时按 jockey_id 解析全名**：与截断文字无关，永不误配（佐々木大 vs 佐々木大輔 这类前缀冲突天然免疫）。
4. **test-data 断言**：crops 中不存在"是另一个骑手名真前缀"的骑手名（截断残留 = 0）；所有 jockey_id 都能在字典中解析。
5. **比赛结果页（SP 接口）直接读本賞金（红利，2026-08-19 实测 13/13）**：`race.netkeiba.com/race/result.html?race_id={id}`（UTF-8）页内 `<span>本賞金:1着,2着,3着,4着,5着万円</span>` 直接给出**付加賞-free 的本賞金**（例：京都新聞杯 `5400,2200,1400,810,540` → 1着 5400万）。**早期"db 域比赛页 4/5着 反推"方案已降级为回退**（db 域 `/race/{id}/` 全页无"本賞金"字样，13/13 实测；`本賞金 = 4着獲得/0.15 = 5着獲得/0.10` 仍保留为 `compute_honsho_prize` 回退）。仅在"重賞且本方 1/2着"时需要。
6. 未来其他源（NAR 等）、调教师/马主同类问题同一机制扩展。

### 6.2 为什么这么设计（服务数据大盘的检索/过滤）

- `facet` 分两层：`search_text`（唯一模糊层）+ 结构化字段（强匹配层），互补不互替，详见 §6.3。
- `facet.血统祖先`：5 代树 62 节点扁平化成**成员集合** → "祖先含 Northern Dancer"是精确成员判断，不是子串（搜 Dancer 不会误中母名/竞走名）。
- `facet.has_races/has_win/has_graded_win/主要場地/有地方/有海外`：布尔/集合过滤条件预计算，一字段命中。
- `stats`（语义，数值字段供范围过滤）与 `facet`（检索索引）分离，职责单一。
- races 内嵌（MB 级免 join）；将来数据暴涨可拆 `data/races/{id}.json` 按需加载，facet 不依赖内嵌，口子已留。
- `_meta.schema` 版本号，前端按版本兼容。
- **前端迁移影响**：顶层裸数组 → `{_meta, horses}` 是 breaking change，`index/detail.html` 读数据处改一行；趁大盘一起改。

### 6.3 查询模型：模糊 / 强匹配 / 数值范围（三层）

`search_text` 只解决"模糊"这一层；**强匹配由结构化 facet 字段承担**，两者互补不互替：

| 层 | 数据 | 匹配方式 | 例子 |
|---|---|---|---|
| 模糊全文 | `search_text`（全字段拼接） | 小写 substring | "ドバイ" → 跑过迪拜的马；"メイクデビュー" → 出道战 |
| 强匹配·等值 | 标量字段：`馬名`/`曾用名`/`性別`/`生年`/`登録状態`/`調教師`/`馬主`/`生産牧場`/`fno` | `===` | 調教師 = 中竹和也（不会误中"ノーザン"） |
| 强匹配·集合成员 | 数组字段：`騎手`/`場名`/`格`/`血统祖先`/`主要場地` | `Array.includes` | 血统祖先含 Northern Dancer |
| 数值范围 | `stats` 数值字段（賞金合計/収得/出賽数/勝…） | 比较运算 | 賞金合計 ≥ 1亿 |

规则：
1. **归一化在构建时做一次**：facet 所有字符串值 NFKC + 去全半角空白 + toLowerCase；前端只做朴素 `===` / `includes`，不带任何归一化逻辑。原始展示值保留在马档案顶层字段。
2. **搜索框两段式**：输入 q → 先对 `馬名`/`曾用名` 精确等值（命中置顶），再做 search_text 模糊——"レッドスカイ"精确命中自己，不被血统里的"スカイ"淹没。
3. **数组字段 = 集合语义**（去重后的成员），不做子串；"含任一/含全部"由前端决定。
4. **人工字段**（译名/近况/备考/血统分析）只进 search_text，不做强匹配（值不稳定、非枚举）。
5. **比赛属性过滤**（距離/馬場/状態 等）量小（407×~30 行），前端直接扫 races 即可；若大盘需要可把去重集合（如 `距離`）加进 facet，设计上留口子。
6. 407 匹规模逐匹扫描 facet 已够快；将来要"带计数的分面导航"，升级为 `_meta.index` 倒排表（`{字段:{值:[id...]}}`），per-horse facet 不变、只加一层汇总。
7. **姓名字段（骑手/调教师/马主）在契约B 层已做全名归一化**（§5.1），facet 数组值直接用归一化后的全名，保证强匹配可靠。
